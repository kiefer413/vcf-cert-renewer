# VCF Certificate Renewer v1.4.0

v1.4.0 adds production-validated VCF Automation external TLS renewal while
preserving the existing Operations, SDDC Manager, vCenter and NSX renewal scope.
The Automation endpoint is selected from Fleet inventory; no endpoint hostname
is hardcoded. Only the fully managed, customer-managed External CA TLS leaf is
eligible. Runtime-managed Automation VMCA TLS, including `automation-internal.example.com`, and
Automation VMCA roots remain discover-only and non-mutable.

The workflow uses Fleet to generate the CSR and retain its private key, signs
that CSR through the configured ACME DNS-01 flow, imports the signed chain,
requests Fleet replacement, and verifies the expected certificate over live
HTTPS. Fleet may retain historical CSR records after replacement. CSR reuse
therefore requires client-side validation of current resource identity,
Automation appliance identity, endpoint and DNS SAN. Foreign, stale, incomplete
or SAN-mismatched records are not reused; ambiguous genuinely matching records
fail safely. Production validation completed the Fleet discovery and CSR generation, ACME
signing, certificate import, Fleet replacement workflow (`COMPLETED`), and live
HTTPS verification for the discovered Automation endpoint, represented here as
`vcfa.example.com`; the served certificate was issued by Let's Encrypt YR1.
After the CSR-history fix, the operator reports that the targeted plan for that
endpoint and `plan --all` succeeded. A subsequent live,
mutating scheduled `renew --all` has not been run. The internal Automation VMCA
endpoint remained unchanged during the validated replacement.

Signer configuration is checked before renewal. Obvious placeholder/example
production settings fail before lego starts. lego diagnostics are bounded and
sanitized, failure reports identify confirmed and uncertain mutations, and ACME
account errors give recovery guidance without deleting or re-registering an
account automatically.

Configuration documentation now distinguishes a repository-local `.env`
template from values actually loaded by the direct CLI and documents supported
environment, `*_FILE`, YAML, secrets-file, systemd Credentials, container and
Kubernetes mechanisms.

See [VCF Automation behavior](../vcfa.md), [secret handling](../secret-handling.md)
and the [container deployment guide](../../CONTAINER_DEPLOYMENT.md). The v1.4.0
image becomes available only after an explicitly authorized release push and
successful release workflow; until then use the published v1.3.1 image.
